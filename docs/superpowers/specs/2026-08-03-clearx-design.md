# ClearX 设计规格

## 目标

ClearX 是 macOS 14 及以上系统上的只读磁盘空间分析工具，使用 Swift、SwiftUI 和 Swift Concurrency 构建。它参考 OmniDiskSweeper 的多列目录浏览方式。本文件描述未来持久化扫描快照和事件驱动增量校验的设计；当前实现仅使用会话内存缓存。

应用名称为 `ClearX`，Bundle 标识为 `com.hang.clearx`。MVP 不删除、移动、修改或在 Finder 中显示扫描项目，不请求“完全磁盘访问权限”，不支持网络卷，不引入除 `GRDB.swift` 以外的第三方包。

## 用户体验

启动页显示一个“本机磁盘”入口、可写外接本地卷以及文件夹选择器；隐藏 APFS 辅助卷、只读系统卷、磁盘映像与网络卷。每个选中的扫描源均在独立窗口中打开。

结果窗口是 Finder 风格的横向多列目录浏览器。选中目录后，子项在下一列中显示。每行显示名称、格式化大小与占父目录比例，固定按大小降序排序，大小相同再按本地化名称升序。MVP 不提供其他排序方式。

首次扫描持续发布部分结果，且可取消；取消后保留并标记不完整结果。再次打开有完整缓存的扫描源时，立即展示缓存树与上次同步时间，并在后台静默校验。正常同步只在工具栏显示低干扰状态；不完整、权限不足、事件历史丢失、完整重扫或失败才显示明确状态。工具栏提供“重新完整扫描”，在新快照提交前持续显示旧结果。

## 模块边界

- `SourceCatalog`：发现本机磁盘与可写外接卷，并管理已扫描来源。
- `ScanCoordinator`：全局 actor，所有来源共用最多四个元数据扫描任务；当前聚焦窗口优先。
- `FileTreeScanner`：枚举目录、批量读取 URL 资源值、汇总大小，并产生完整性信息。
- `EventValidator`：管理每卷 FSEvents 检查点，决定缓存是否直接有效、局部刷新或完整重扫。
- `SnapshotStore`：以 GRDB 封装 SQLite WAL、Schema 迁移、事务、快照切换和按列查询。
- `ResultWindowModel`：只保留可见浏览器列、选择状态与扫描状态；不持有整棵目录树。

扫描和大小聚合始终在主 actor 外执行。`SnapshotStore` 是 SQLite 的唯一访问入口；SwiftUI 通过结果模型读取查询结果。

## 数据模型

每个 `ScanSource` 保存稳定的来源 ID、卷身份、作为 `URL` 的根位置、活动快照 ID、最后成功处理的事件检查点、完整性、最近使用时间和缓存状态。对外的扫描源、事件与诊断值均使用 `URL`；仅数据库内部为节省空间使用节点名称与父节点 ID 等紧凑字符串。

快照使用紧凑层级而非重复完整路径。每个节点保存父节点 ID、本地名称、项目类型、已分配大小、可取得的内容修改日期、完整性标记和可选的会话内文件身份信息。完整 URL 按父链按需重建。

全量扫描写入独立的候选快照。候选完成后，通过一个事务切换 `ScanSource` 的活动快照指针。旧快照在切换前一直可供界面读取；取消、崩溃或失败不会影响它。已知变更分支的刷新在单个事务中替换旧子树、插入新节点并更新祖先聚合大小。

快照数据库保存于 ClearX 的本地 `Application Support` 目录，排除云同步和备份。MVP 依赖 macOS 用户帐户和 FileVault，不采用数据库级加密。缓存总预算为 1 GB；超限时淘汰最久未使用且当前不可访问来源的完整快照，并在来源列表标记“缓存已清理”。若缓存已超过 1 GB 且不存在可安全淘汰的不可访问来源，显示“缓存空间不足”并停止持久化新的候选快照；不得静默删除可访问来源的缓存。

## 扫描规则

扫描包含隐藏文件和包目录内容，不跟随符号链接，不跨越根目录之外的挂载卷。不可读项目被跳过，父级保留可访问聚合值并标记不完整。目录大小是已扫描后代的总和。

文件大小使用系统提供的已分配大小。硬链接在同一扫描中按临时文件系统对象身份去重：首次遇到的位置计入，后续位置保留并标记不额外占用。APFS 可能共享内容块的克隆文件不属于此规则，不尝试分摊物理块，仍显示系统提供的已分配大小并提示其可能不同于可释放物理空间。

已取消或不完整快照可以展示，但绝不作为增量校验基线；下次打开时自动对整个根目录完整重扫。

## 缓存校验与刷新

完整快照记录每卷 FSEvents 检查点。完整扫描或分支刷新前，`EventValidator` 先建立设备级事件流，固定一个事件高水位，并在提交前处理直到该水位的全部事件；节点变更与已处理水位在同一个数据库事务中提交。水位之后到达的事件保持待处理状态，绝不提前标记为已同步。

再次打开时，`EventValidator` 以设备级事件流从该检查点重放历史，并在重放成功完成后判定：

1. 没有新事件：事件检查点证明扫描源未变，直接使用缓存并结束同步。
2. 事件指出明确变化路径：合并约 1 至 2 秒。文件、删除项目和不存在目录的路径向上归一化到扫描根目录内最近的可访问父目录；验证其仍位于预期卷后，以最浅目录去重并只重扫这些分支。
3. 事件历史丢失、`RootChanged`、`UserDropped`、`KernelDropped`、`MustScanSubDirs`、事件 ID 重置或回绕、检查点或卷 UUID 不匹配、事件流失败、卷或根目录身份变化、路径越界、元数据不可用或事件语义不明确：不能证明缓存有效，完整重扫该源。FSEvents 事件 ID 的普通数值跳跃是全局日志的正常现象，不得单独视为事件丢失。

内容修改日期不用于证明全局缓存有效性，仅在已确定要刷新分支时参与细粒度比对和诊断。根目录不可访问时标为“不可用”并保留快照，不能据此删除缓存；已验证刷新中发现不存在的节点则自动移除。

结果窗口保持打开时继续监听事件，以相同合并和分支替换规则刷新。多个窗口可以同时扫描，但共享四任务全局预算，聚焦窗口优先。

## 可靠性与恢复

所有索引写入必须是事务性的。数据库打开、迁移或校验失败时，隔离损坏数据库并自动重建受影响来源；这不得阻塞新的完整扫描。文件系统事件只能作为优化，任何不确定性都向完整扫描倾斜。

状态模型明确区分空闲、扫描中、已完成、已取消、不完整、权限受限、不可用和同步失败。错误文本及所有用户可见文本使用简体中文，并从 `Localizable.xcstrings` 提供。

## 性能策略

扫描使用单个有界调度器，最多四个元数据工作任务，避免无限并发造成 I/O 争用、文件描述符膨胀和界面卡顿。SQLite 使用 WAL、显式索引、批量事务写入及受控写入路径。

浏览器按可见列惰性查询数据库并有限预取行，不将百万级节点树载入 SwiftUI 状态。目标是在缓存的百万节点来源上 1 秒内显示首列；无变更重复打开在 3 秒内完成校验；一万项已知变更仅刷新相关分支并在 5 秒内提交。首次完整扫描记录吞吐与峰值内存，但不设统一耗时门槛。

## 验证策略

文件系统边界通过协议隔离，以便使用临时目录和注入事件流测试。测试覆盖聚合、稳定排序、隐藏文件、包目录、符号链接、硬链接、APFS 共享内容提示、不可读项目、取消和不完整快照。

持久化测试覆盖 Schema 迁移、候选快照切换、子树替换、检查点与节点的原子提交、扫描或分支刷新期间的变更、事件重放完成、事件历史丢失或含糊标志回退、事件路径越界、删除路径归一化、数据库隔离与重建、1 GB 缓存淘汰。结果模型测试覆盖缓存直显、静默同步和异常状态。基准测试生成可重复目录树，验证既定百万节点、无变更和一万变更阈值。

## 延后决策

- 安全清理不属于当前 MVP。后续设计必须遵循：默认仅勾选低风险项，高风险项只展示或要求二次确认；每项清理均说明其性质、空间来源、可清理理由和清理影响；所有数据与处理留在本机，不上传路径、文件名、依赖列表、项目结构或清理记录；优先调用官方工具；开发者模式不读取源码内容，只统计依赖目录、lockfile 状态、缓存与构建产物。
- 对外发布前决定 Mac App Store、Developer ID 或双渠道分发，再设计 App Sandbox entitlement 与文件访问权限模型。
- 发布前添加并验证访问文件修改日期所需的隐私清单声明。
